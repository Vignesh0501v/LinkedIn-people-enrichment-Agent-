## Phase 4 (2026-08-19) — Docker, dedicated chat DB, LangChain, richer chat UX

New scope confirmed with Vignesh after unit 12 shipped and was live-tested. Four architecture forks were confirmed explicitly before starting (matching this project's established practice of not guessing on forks — see unit 11's agentic-vs-deterministic precedent):

1. **LangChain scope: wrap the 2 existing Groq calls only** (ChatGroq + prompt templates + structured output parsing), NOT a LangGraph rewrite of the orchestration. NFR-07 (never give Groq tool-calling/agentic access) is unchanged and still applies — this is a plumbing swap, not a new capability.
2. **Chat session/turn history moves to a dedicated database** (Postgres, via SQLAlchemy, provisioned in Docker Compose) instead of Redis. Redis keeps its existing jobs unchanged (search-result caching, batch/row resumability, mapping-template storage) — this is Session/Turn only.
3. **Output-format decision (table-in-chat vs. `.xlsx` download) is a 3rd field on the existing Groq intent-extraction schema** (`output_format`), not a separate LLM call and not pure keyword matching.
4. **Both frontend and backend get Dockerized**, frontend via a production build served by nginx (not a dev-server container).

New units:

22. **Docker Compose: backend + frontend + postgres services** — owner: backend-developer — depends on: none — done when: `docker-compose.yml` runs `redis` (existing), a new `postgres` service, a `backend` service (Dockerfile building `uvicorn app.api:app`), and a `frontend` service (multi-stage Dockerfile: `npm run build` then nginx serving the static output) — all networked so the frontend's built-in API base URL resolves to the backend container, and the backend's `DATABASE_URL`/`REDIS_URL` resolve to the `postgres`/`redis` service names, not `localhost`. **[DONE]**
23. **Postgres-backed Session/Turn store + session-list endpoint** — owner: backend-developer — depends on: unit 22 (needs `postgres` service to develop against, or a local Postgres for dev) — done when: `Session`/`Turn` persistence (currently `app/session.py`'s Redis-backed `SessionStore`) is backed by Postgres via SQLAlchemy instead, `GET /sessions` (list, newest-first, with enough of a preview — e.g. first turn's text/filename and last-active time — for a sidebar row) is added, and the `mapping_proposal` turn payload is enriched to carry `columns`/`sample_rows` (currently missing — this was the reload gap flagged when unit 12 shipped) so a reopened session can fully reconstruct the mapping-editor UI, not just display it as inert history. **[DONE]**
24. **LangChain-based GroqClient + externalized prompts** — owner: backend-developer — depends on: none (independent of 22/23) — done when: `app/intent_extraction.py`'s `GroqClient` is rebuilt on `langchain-groq`'s `ChatGroq` + prompt templates + a structured-output parser, preserving the exact same public methods (`propose_mapping`, `extract_single_lookup_fields`), the same retry-once-then-fail-safe discipline, and the same model (`openai/gpt-oss-20b` — per Vignesh, keep whatever's currently free/available on Groq, revisit the specific model choice later). System/user prompt text moves out of Python string constants into a JSON file (e.g. `app/prompts.json`), loaded at runtime. `app/verification.py` keeps reusing the same client class, unchanged in spirit. **[DONE]**
25. **Greeting detection, output-format field, and conversation context window** — owner: backend-developer — depends on: unit 24 — done when: the same Groq intent-extraction call gains two things: (a) an `intent` classification (`greeting`/`chitchat` vs. an actual data request) so a plain "hi" gets a friendly conversational reply instead of being run through ingest/mapping as if it were a lookup, and (b) an `output_format` field (`table`/`excel`) derived from the user's phrasing, capped by row count — table-in-chat only allowed below a small row-count threshold (exact cap TBD by backend-developer's judgment, since dumping a 500-row batch as a chat table is unusable regardless of what the user typed; NFR-04's 200-1,500 row scale makes this a real constraint, not a hypothetical). The call also now receives the last 5 turns of the session's history as conversational context, so short follow-ups ("actually search at Acme instead") resolve correctly. **[DONE]**
26. **Excel output gains a Summary sheet** — owner: backend-developer — depends on: unit 19 — done when: `download_batch`'s workbook has a second sheet with counts by `match_status`, the criteria/search_mode used, row count, and a timestamp — not just the raw per-row Results sheet it has today. **[DONE]**
27. **Frontend: session-history sidebar, table-vs-download rendering, Docker** — owner: frontend-developer — depends on: units 23, 25, 26, 22 (needs the new `/sessions` list endpoint, the enriched mapping-proposal payload, and `output_format` on batch results before it can be built correctly) — done when: a sidebar lists past sessions (newest first) that can be clicked to reopen and continue a conversation (using the enriched turn history from unit 23); a completed batch renders its results as an inline chat table when `output_format == "table"` instead of only ever offering a download; the frontend has a production Dockerfile (build + nginx) wired into `docker-compose.yml`. **[DONE]** — live-verified 2026-08-19 against the real Docker Compose stack (all 4 containers, not a dev-server substitute): greeting detection correctly skips the pipeline; a real single-lookup ran mapping → criteria → search → verify → a genuinely correct `VERIFIED` match (Bill Gates' actual LinkedIn URL); `output_format: "table"` rendered inline with a secondary download link, exactly as specified; the sidebar correctly hides empty (0-turn) sessions; reopening a session fully reconstructed its history including the completed result; continuing the reopened session appended to the same `session_id` (confirmed via `GET /sessions` turn counts) rather than starting a new one. One infra fix made outside either agent's scope: `docker-compose.yml`'s `postgres` service published host port 5432, which collided with an unrelated project's container already running on this machine — remapped to `5433:5432` (container-internal port, and thus the `backend`→`postgres` connection, unaffected).

**Why this is being tracked as a formal phase rather than ad hoc changes:** several of these are genuine infrastructure/architecture decisions (a second database, a new LLM plumbing layer) that later sessions need to find recorded, not rediscover by reading diffs.

**How to apply:** units 22 and 24 have no dependencies on each other and can run in parallel. Unit 23 needs 22's Postgres service available. Unit 25 needs 24's LangChain client landed first (same file). Unit 27 (frontend) is last — it needs the new session-list endpoint, the enriched mapping-proposal payload, and the output_format field to all exist first, otherwise it'd be built against contracts that don't exist yet.

## Sequencing notes

- Units 13 (session/intent-extraction) and 14 (paste ingestion) are independent backend work and can run in parallel; both feed unit 16 (API contract).
- Unit 15 (single-lookup) depends on both 13 and 14 since a single lookup can arrive as either a typed instruction or a tiny pasted row.
- Unit 12 (the chat frontend) is the one unit still blocked on an API contract landing first (unit 16) — same contract-before-consumer ordering as before, just against the new session-oriented contract instead of the old batch-only one.
- Units 17–19 (scoring → verification → output) are unaffected by the UI pivot and can proceed independently of units 12–16 once units 7 and 9 are done — which they are.
- **Deferred cleanup (from unit 20), not yet a Plan unit**: consolidate the duplicated Redis-store boilerplate (`SessionStore`/`TemplateStore`/`BatchStore`), the three near-identical `FakeRedis` test fixtures (now four, after unit 20 added `tests/test_batch.py`'s own copy), and the duplicated Groq retry/fail-safe control flow between `intent_extraction.py`/`verification.py`. Worth its own dedicated pass rather than folding into a future feature unit.
